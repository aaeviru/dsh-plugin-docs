# 文档仓库的 Issue、分支与 PR

本仓库沉淀 DSH 插件开发与安装经验。本文件管理资料调查和文档修改；[第 08 篇](08-codex-workflow.md)保留向 Coding Agent 派发插件实现任务的经验，两者适用范围不同。实际修改插件代码时，遵循插件仓库的开发流程。

## 选择任务范围

拼写、格式、失效链接等小修改可直接创建文档分支和 PR，不强制单开 Issue。新增专题、跨多轮资料调查或需要持续追踪的纠正，先查现有 Issue；相同问题补充原讨论，独立交付物再新建 Issue。

调查说明保持简短：要回答的问题、资料或版本范围、预期文档和停止条件。调查中可以记录不确定性，不要求预先写完整实现 Contract 或承诺一个结论。

安装命令、权限、API、业务、架构或 agent 工作规则的变化需要说明依据、影响和验证办法，不能因为载体是 Markdown 就按拼写修正处理。

## 分支与交付

纯阅读和已授权的讨论不需要分支。修改文件时，从最新 `main` 创建 `docs/<issue>-<slug>`；没有独立 Issue 时使用 `docs/<slug>`。并行写入使用独立 worktree，保留其他任务的未提交内容。

一个持续调查 Issue 可以关联多个文档 PR。PR 交付一项可审阅的专题或修订：尚未结束的讨论使用 `Refs #<编号>`，仅在完整交付 Issue 约定范围时使用 `Closes #<编号>`。不要为每条补充资料新建 Issue，也不要让长期讨论绑定一个永久文档分支。

## 内容与验证

| 内容 | 检查与证据 |
|---|---|
| 编辑修正 | 差异、`git diff --check`、Markdown 格式和链接目标 |
| 新资料或经验总结 | 原始来源、上下文、适用环境与版本；区分观察、推论和建议 |
| 安装、构建、API 或权限指导 | 对照实现或官方来源，按影响补充可复现验证；说明实测环境、未执行项和剩余限制 |
| 协作流程和 agent 指令 | 核对任务分类、授权与角色边界、现有规定及读者入口是否一致 |

用于操作的技术指导需经相应技术审阅，关键或有争议的结论需独立核对。自测记录与独立审查分别说明；实际声称经过独立审阅时记录审阅者与版本。

没有实测的命令或平台，标明资料依据与“未实测”的范围；只有格式检查通过时，不能宣称安装或运行已验收。需要实施验证但暂时不能取得证据时，保持候选说明或草稿 PR，写清缺口，不把未验证指导呈现为已验证步骤。

新增章节时更新 README 的目录及相关交叉引用。修改既有说明时检查相邻章节和对应语言版本，修正相互冲突的指引。PR 说明问题、修改、依据、实际检查、未验证项和影响。

## 合并与清理

人类决定是否合入。合并一篇经验记录不自动确认其他版本或平台兼容，也不代表其中的架构提案已获批准。相关 Issue 是否完成，依据它自己的问题与交付范围判断。

确认提交已保留、PR 状态明确且工作树干净后，删除本任务分支和 worktree。保留仍在进行、承担恢复用途或由其他 agent 使用的工作。
